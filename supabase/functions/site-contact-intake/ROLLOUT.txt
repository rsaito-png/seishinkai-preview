The public function is fail-closed. It stores a row only when the Edge Function
secret CONTACT_INTAKE_ENABLED is exactly the four letters true. Any other value,
including unset, "1", "TRUE", or "True", returns HTTP 503 with
{"ok":false,"stored":false,"lead_event":false,"code":"not_configured"}
and does not open a database connection, classify the text, or count a lead.
The browser switch in assets/contact-config.js does not open the API by itself.
A direct POST to the function URL is refused by this server gate.

Database region of project zvrardoyxocmqhvyddnf is ap-northeast-1 (Tokyo) for Postgres.
That region does not by itself keep every Supabase log, auth event, or edge invocation inside Japan.
Do not put inquiry text in logs.

Public RPC wrappers are security invoker. The private functions they call are

Schema: supabase/functions/site-contact-intake/schema.sql
anon cannot execute the inbox functions. authenticated can call them, and the
function raises 42501 unless the JWT user is that account. The table is not in
the Data API schemas, RLS is forced with no policies, and API roles have no
table grants. Do not add site_contact to exposed schemas.

Rate limits that are actually enforced, in the database transaction:
  same email address: 5 accepted intakes per Japan calendar day
  whole function: 30 accepted intakes per Japan hour
Supabase documents Sb-Forwarded-For only for Auth rate limits, and only on a
request that uses a secret key (https://supabase.com/docs/guides/auth/rate-limits).
Edge Function examples read x-forwarded-for, and no official page says the
platform overwrites a caller-supplied value. This function does not use
x-forwarded-for, x-real-ip, or the gateway connection address as a visitor id.
Those headers are not a per-person limit. The global cap is the abuse ceiling.
A missing Origin header is not treated as authentication. Disallowed browser
origins are still rejected when intake is enabled. Validation, the honeypot,
the minimum fill time, and the size limit still apply.
